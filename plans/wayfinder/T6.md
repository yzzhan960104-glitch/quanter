# state_store SSoT 在演进优先下的演进决策

## Question

state_store SSoT 在"演进优先"姿态下如何演进？决策点：

1. **plan→SQLite 是否重启**：之前推迟的 `plan → SQLite`（独立 `trading_plans.db` + 状态机 + audit，不并入 position_book）——在演进优先姿态下是否现在重启？（memory: plan-sqlite-deferred，原推迟到"live P0 四项后"）
2. **多策略/多账户状态隔离**：SSoT 如何支撑多策略/多账户——每策略/每账户独立状态空间？还是 schema 加 `strategy_id`/`account_id` 隔离键？与 T3 隔离模型联动。
3. **现有表的扩展路径**：account / trade_event / order / fill / position_book / review_report 等表如何承接三维扩展。
4. **读写键对齐治理**：历史坑（actual_sid 死字段、stoploss 复用、双写幂等）的系统性治理——是否建 schema 契约测试防再生。

## Resolution

**四决策点定稿（2026-08-15 收口，决策散落于各治理门与波次落地，此处归账）**：

1. **plan→SQLite 不重启（DG-5 划线）**：生产真相只信 trade_event 表，plan 生命周期已由 SIGNAL/CONFIRMED 状态机 + DB 写入承接（Phase C 全治理 2026-08-12：`save_plan`/`confirm_plan` 已删、`load_plan` JSON fallback 窗口关闭）。独立 `trading_plans.db` 不建——SSoT 单库原则优先，memory「plan-sqlite-deferred」就此销账。
2. **多策略/多账户状态隔离 = W3 划线**：schema 是否加 `strategy_id`/`account_id` 隔离键由 [T3](T3.md)（多账户隔离与路由）的隔离模型决定，本工单不预铺——避免为未定形态提前改表（反过度设计）。
3. **现有表的扩展路径 = Phase A/B/C 已治 + fill.direction CHECK**：account/trade_event/order/fill/position_book 的三维扩展承接以「先契约测试、后扩列」为路径；本波次（2026-08-15 技术债 T3）补 `fill.direction` CHECK 约束封死「非 'BUY' 一律按 −qty」的符号静默翻转。
4. **读写键对齐治理 = 三件落地**：① `is_vetoed` 单点（T11 · commit `710d9c30`）② `actual_sid` DB 单源（M2 · T14 · commit `ccaad5c9`，断 broker-first 潜伏 import 环）③ `StopLossContext` 容器装箱（T11，orchestrator 单参调 `stop_loss_monitor`）。历史坑（actual_sid 死字段/stoploss 复用/双写幂等）的系统性防再生以契约测试 + 单源常量形态就位（G7 终态集单源 `4a29362f` 同族）。
