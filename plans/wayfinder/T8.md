# 架构演进的依赖态度边界

## Question

架构演进是否允许引入新依赖？需敲定**引入边界**（写成决策记录，作为所有重构工单的约束）：

1. **基线立场**：严格守 Karpathy 极简（纯标准库 + `Protocol`/`ABC`，无 DI / 事件总线 / ORM 框架）还是允许选择性引入？
2. **分层解耦 + 可插拔适配层**（T2）在纯标准库下能否实现？（大概率能，但要拷问痛点：插件发现、配置组合、生命周期钩子是否需要框架支撑）
3. **多账户硬隔离**（T3 若选硬隔离）若需子进程/IPC，是否引入 `multiprocessing` 之外的依赖？
4. **绝不引入清单**：哪些类别的依赖一律拒（重型量化黑盒框架、魔法 DI 容器、隐式事件总线等）。
5. **可引入清单（如有）**：哪些轻量、显式、可审计的依赖可考虑，审批口径如何。

## Context

- 横切决策。CLAUDE.md 强约束：拒绝重型黑盒框架、显式至上。
- 三维扩展（尤其多账户硬隔离）可能诱发"引入消息总线/IPC 框架"冲动。**必须先定边界**，避免各工单各自引入造成依赖爆炸、违背极简哲学。
- 与 T2（适配层契约）联动：接口实现选型受依赖边界约束。

## Notes

- 主流程：`mattpocock-skills:grilling`。
- 拷问：每提一个"引入候选"，必须回答"纯标准库为什么不行？引入后的可审计性/调试性/锁版本成本？"。
- 结论写成 `docs/` 下的决策记录（ADR 风格），链接到 Resolution。

## Resolution

**决策已落 ADR-10（2026-08-12，W0 护栏批，commit `82a614a8`）**：[docs/architecture/10-t8-dependency-policy.md](../../docs/architecture/10-t8-dependency-policy.md)——五决策点全部定稿：① 基线立场 = 严守 Karpathy 极简（纯标准库 + `Protocol`/`ABC`/`dataclass`）；② 适配层 T2 纯标准库可实现（论证：插件发现 `importlib` / 配置组合 `dataclass`+dict / 生命周期钩子 `Protocol` methods，不需要 DI/事件总线/插件黑盒）；③ 多账户硬隔离若需子进程 → 标准库 `multiprocessing`，不引入 IPC 框架；④ 绝不引入清单（重型量化黑盒框架 qlib/backtrader/vnpy、魔法 DI 容器、隐式事件总线、ORM）；⑤ 可引入清单暂空 + 三问审批口径（纯标准库为什么不行/可审计性成本/更轻替代）。

**已实际执行佐证**：W1-A/T2 keystone 与 2026-08-15 技术债波次 W2（broker 分层 + BrokerProtocol + Ports 化）全程零新增依赖落地——边界经住了两波次重构的现实拷问。
