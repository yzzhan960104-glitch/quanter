# data 完整性生产 gate + 自动补采重构

## Question

> ⚠️ **[T12](T12.md) 实证（2026-08-08）**：daily 双轨（`sync_daily_incremental` vs `sync_tushare.py daily`）+ 通用同步器**无写入前历史行数守卫**，致 a_shares_daily 被 `sync_tushare.py daily` 残片覆盖（**1020万行 → 3200行**）。本工单的 **④ daily 双轨收口** 与新增的**「写入前历史行数守卫」**须置顶为最高优先（防再发）。

按 [T5](T5.md) 根治方案重构 data 完整性闭环（5 项）：

1. **scan_integrity 升级为生产链强制 gate**（接 `ops/data_pipeline.py` T1/T2 + 每周全扫调度）；
2. **repair_gaps 升级为自动补采触发**（scan FAIL → 自动 repair，受配额/熔断守卫）；
3. **完整性维度收敛 `data/integrity.py`**（新增 D5 复权一致 / D6 列完整 / D7 跨湖时区 / D9 行数阈值告警）；
4. **daily 湖双轨收口**（`TUSHARE_DATASETS` 删 `"daily"` key，唯一写入口 = `sync_daily_incremental`）；
5. **repair_gaps 裸调 pro 接口改走 `_fetch_with_guard`**（限频守卫，防裸奔）。

用 prototype 验证 scan→repair 闭环 + gate 接生产链后**不阻断正常交易日**（gate FAIL 的降级语义：阻断交易 vs 跳过标的 vs 告警继续）。

## Context

毕业自 [T5](T5.md)。T5 根因：生产 gate 只校验实时性、scan/repair 是孤立 CLI 无调度、历史缺口被动跳过永不发现。**blocked by [T12](T12.md)**（先确认活债真因，否则在单日湖上重构 gate 无意义——find_gaps 返空会让 scan 看起来"全绿"）。
