# miniQMT → 券商托管执行：迁移可能性调研（2026-08-20）

> 命题：现架构 = 自研系统跑本机 + miniQMT 客户端本地执行（xtquant）。调研「把脚本上传到券商侧托管执行」（关机可跑、无人值守）的可能性。姊妹篇：[2026-08-20-futu-integration-feasibility.md](2026-08-20-futu-integration-feasibility.md)（富途 OpenAPI 接入；本文的富途量化云是其内置平台托管面）。

## 一、TL;DR 裁决

| 通道 | 托管真身 | A 股直连 | 能否装下本仓库系统 | 一句话 |
|---|---|---|---|---|
| **PTrade（恒生）** | ✅ 券商服务端真托管（关机可跑） | ✅ 全品种（股/两融/基金/债/可转） | ❌ 仅内置库+默认禁外网 | 字面命题的唯一现实 A 股通道，但只装得下「重写后的单策略」 |
| **富途量化云 AlgoCloud** | ✅ 富途云端（关客户端不停策略） | ❌ 港/美/A股通；内地身份禁买入（合规 P0，见姊妹篇 §三） | ❌ 仅 Python 标准库、50 标的/策略 | 港美轻量策略备选，合规未决前不可用 |
| **QMT 上云 VPS（伪托管）** | 自租 Windows 云服务器 | ✅ 原通道不变 | ✅ **零改动整体上云** | **推荐正解**：解决的正是托管的原始诉求 |
| 迅投 ThinkTrader 云策略 | 迅投自家云（一句话/拖拽建策略） | 视券商对接 | ❌ 平台内策略，非工程载体 | 面向轻用户，非本系统形态 |
| 券商策略托管服务 | 券商机房（东北证券等，双中心部署） | ✅ | ❌ | 面向私募/机构的机构服务，个人不适用 |

**总裁决**：
1. 「上传脚本到券商执行」的通道**存在**（PTrade / 富途量化云），但都要求策略在券商沙箱内**自包含**——数据用券商的、逻辑用沙箱受限 Python 重写。本仓库工业级系统（data_lake 43 数据集、discovery/autopromote、engine 四 job、ADR-16 风控、fill 真相源）**没有任何券商沙箱装得下**。
2. 混合架构（本地算信号 + 券商侧只执行）被沙箱**默认禁外网**堵死——托管脚本收不到外部信号，逻辑必须搬进去（PTrade 国盛版外网例外见 §五，脆弱不押注）。
3. 托管原始诉求（无人值守、不依赖本机、防误杀）的**最小改动解 = Windows 云服务器跑现有全套**（§七方案 A）；若接受策略重写+风控降级，PTrade 试点是唯一真托管路径（§八）。

## 二、动机对照（为什么想迁移）

现状痛点（皆有事故记录）：

| 痛点 | 事故/事实 |
|---|---|
| 本机必须开机且客户端在 | QMT 客户端被杀/劫 session：08-18 凌晨并行测试劫客户端、傍晚杀引擎（两杀生产） |
| session 单进程独占 | miniQMT userdata + sid 互斥，多会话/多任务共用一台机器必冲突（`broker/qmt_connection.py` sid 轮换自愈是补丁不是解） |
| 本机环境即生产 | 2026-08-14 引擎无客户端 connect 挂死 lifespan；完整性闸漏采拒跑 daemon |
| 断电/断网/休眠 | 本机 Windows 桌面环境不可 SLA |

「券商托管」直觉上全解——但代价见 §四。

## 三、通道事实盘点

### 3.1 PTrade（恒生电子）——A 股唯一的个人可及真托管

- **运行模型**：策略上传券商服务端，`initialize(context)`（启动一次）→ `before_trading_start`（盘前）→ `handle_data(context, data)`（盘中按分钟/日频循环）→ `after_trading_end`（盘后），事件驱动；关机/关软件不影响运行。
- **部署单元 = 单个策略 .py 文件**：策略在 PTrade 客户端编辑器内编写/保存（支持代码加密上传下载）；**无 pip，仅内置三方库**（pandas/numpy/talib/arch 等，版本由券商锁定）；**自定义多文件 import 未文档化**（默认按不支持对待，立项前向券商确认）。唯一的多文件口子是**研究目录当数据仓**——`get_research_path()` 让策略读写 pickle 等数据文件做跨重启持久化（是数据仓不是代码仓）；`g` 全局变量可序列化的部分自动落地，`tick` 级逻辑须用 `tick_data`/`run_interval`。
- **内置 tushare**（数据口径可部分对齐本仓库）。
- **网络**：默认禁外网；已知**国盛证券 PTrade 允许访问外部数据源**（极少数例外）。
- **门槛/费用**：传统 50 万资产免费开通；国金证券双平台（QMT+PTrade）约 10 万即可；有渠道称云端托管加收约 0.1 元/笔（单源未核）。
- **品种**：股票/两融/基金/ETF 申赎/债券/可转债（无期权期货——那是 QMT 的优势面）。

### 3.2 富途量化云（AlgoCloud）——手册平台的托管面

- 牛牛客户端「量化」页策略可选**本地运行**（关客户端即停）或**云端运行**（富途服务器，关客户端/关机不停）；云端权益：开户后免费试用 60 天，V2+ 会员永久（帮助中心 topic638，以官方最新为准）。
- 沙箱约束（手册实证）：仅 Python 标准库、禁第三方、禁硬盘/网络/界面；每策略 ≤50 运行标的；下单 15 笔/30 秒；指标须用平台注册（麦语言/Python 双通道）。
- 市场面：港/美/A股通/期货期权；**A 股直连不存在**，且内地身份买入禁令（2026-05 八部门新规）压顶——合规 P0 未决前整条通道仅模拟盘可用。

### 3.3 QMT 上云 VPS——不是托管，但达成同一目标

- QMT/miniQMT 仅 Windows；可部署阿里云/腾讯云 Windows VPS（最低 2C4G/40G，建议 4C+）；**少数券商不允许云环境登录，选券商时必须先确认**（现有券商是否允许是第一待办）。
- QMT 客户端每日自动退出+需输密码：社区有成熟自动登录/保活方案（知乎/雪球教程），属运维项非阻塞项。
- 变体：miniQMT 留家中内网机器、云服务器做穿透调度（集思录推荐方案）——适合已有闲置内网机的场景。

### 3.4 迅投 ThinkTrader 云策略 / 券商机构托管

- ThinkTrader（thinktrader.net）：迅投自家云策略平台，「一句话到实盘」/拖拽建模，面向个人专业投资者（策略管理）与机构（因子管理）——平台内策略形态，非任意 Python 工程载体。
- 东北证券等提供量化策略托管服务（恒生/顶点/FPGA 柜台、沪深双中心）——私募/机构服务，个人不可及。记录备查，不构成选项。

## 四、判定一：券商沙箱装不下本仓库系统（逐模块对照）

**部署单元本身就是单个策略 .py 文件**（PTrade 客户端编辑器 / 富途量化代码策略同为单文件）——不是「工程目录上传」，连「拆成多模块搬进去」都不成立；研究目录只解决数据持久化不解决代码组织。

| 本仓库模块 | 沙箱里的命运 |
|---|---|
| data_lake（43 tushare 数据集 + parquet 湖） | ❌ 无磁盘、无 pip；PTrade 虽内置 tushare 但仅券商业态可用数据，湖全丢 |
| discovery/autopromote（optuna/hmmlearn 搜索与晋级） | ❌ 库不在内置清单即不可用；晋级链路（engine_hash/快照对账）无宿主 |
| engine 四 job（pre_open 09:22/stop_loss 30s/post_close/pipeline 18:00） | ⚠️ 需按 PTrade 事件模型重写映射（before_trading_start/handle_data/after_trading_end），粒度/时点语义有损 |
| ADR-16 人工风控两值（block_new_orders/max_total_position，sqlite） | ❌ **双值拦截失效**——券商侧无本仓库状态库，人工闸必须另想通道（如策略内读外部条件，但禁外网） |
| fill 真相源/对账/简报/告警 | ❌ 全套失效；成交记录以券商 App 为准，双源真理 |
| 2007 项测试基线/FakePro/FakeOpenD 体系 | ❌ 沙箱无 pytest 环境，重写策略无测试护栏 |

结论：**可托管的形态只有「单策略重写」**（如颈线策略：用沙箱数据+内置指标复刻信号逻辑+下单），不是「系统迁移」。

## 五、判定二：混合架构（本地信号 → 托管执行）基本被堵死

- 富途沙箱禁网络：托管策略无法轮询自建信号服务——堵死。
- PTrade 默认禁外网：同堵；**国盛证券 PTrade 外网例外**理论上可让托管脚本拉本仓库信号（或反向：本仓库推信号到可轮询的端点），但依赖单一券商的宽松政策，随时可收紧，且把实盘可用性押在「例外」上违背本仓库稳健基调——**可试点不押注**。
- 结论：托管的本质要求是「决策逻辑住在券商沙箱里」。

## 六、判定三：PTrade 重写路线的真实成本（若执意真托管）

1. **研发分裂**：同一策略两套实现（本仓库回测/搜索口径 vs PTrade 沙箱口径），参数晋级链路断裂——autopromote 产出的参数需人工搬运进沙箱。
2. **风控倒退**：ADR-16 双值、对账 drift 告警、fill 幂等真相源全部不在场；券商侧仅有 PTrade 自带风控（佣金/阈值类）。以本仓库「人工闸+对账红线」的治理标准衡量是明确倒退。
3. **验证成本**：需先双轨对照（本地 dry_run vs PTrade 模拟/实盘小资金）足够长周期，确认两套口径成交一致——本质是引入第二个执行真相源的成本。
4. 适用场景收窄后：只值得为**成熟的、参数稳定的单一策略**（如已定稿的颈线参数集）做托管冗余，不适合承载演进中的策略族。

## 七、方案 A（推荐）：Windows 云 VPS 整体上云，零改动

**为什么这是正解**：托管的四个原始诉求全部达成，且不付 §四-六的任何代价。

| 诉求 | VPS 方案达成方式 |
|---|---|
| 无人值守 7×24 | 云主机 SLA；QMT 客户端 + `.venv310` + quanter 全套原样搬 |
| 不再误杀 | 专用 VPS 无并行会话（08-18 两杀事故的根治：生产环境不再与人共用） |
| session 独占 | 单机单实例，sid 冲突源消失 |
| 断网/休眠 | 云厂商网络 SLA；Windows 自动更新需显式关闭/排期 |

**实施清单**（1-2 天量级）：
1. **先确认现券商允许 QMT 云环境登录**（少数券商禁止云/虚拟机登录——若现券商不允许，换允许的券商开户或走内网穿透变体）。
2. VPS 选型：Windows Server，4C8G 起（QMT 客户端+xtquant+引擎+数据湖同步的余量）；同地域低延迟非必需（miniQMT 是普通柜台链路）。
3. 搬迁：QMT 客户端装 VPS → userdata 迁移或重登录 → 仓库 clone + `.env` + data_lake 首次全量拷贝（LFS 治理：湖不入 git，走磁盘/对象存储搬运）→ 引擎冷启动校验（按 2026-08-14 复验流程：connect 守护/完整性闸/daemon）。
4. 自动登录保活：QMT 每日退出问题的成熟方案落地 + `ops/trading_supervisor.py` 纳入计划任务。
5. 运维面：远程桌面改用 SSH 隧道/堡垒；Windows 更新排期到周末；磁盘快照策略；告警通道（notifier）依赖的出口网络验证。
6. 成本：4C8G Windows VPS 约 ¥200-400/月（阿里/腾讯同级），对比 PTrade 托管的隐性成本与风控倒退，性价比占优。

**残留风险**：券商风控对云 IP 登录的态度变化（低概率、有感知窗口）；VPS 单点（可接受——本机同样是单点但更脆）。

## 八、方案 B（真托管试点，仅当有强诉求）

若确需「脚本住券商侧」（如长期出差/彻底告别运维）：
1. 选 PTrade 通道：国金（~10 万门槛）或国盛（50 万，但 PTrade 外网例外——若想保留「信号来自本仓库」的混合模式，国盛是唯一候选）。
2. 首个试点策略：**已定稿颈线参数集**的最小重写（initialize 定池 → before_trading_start 取数 → handle_data 信号+下单 → after_trading_end 记录），只用内置库+内置 tushare，逻辑与本地 replay 口径对照。
3. 双轨验收：本地 dry_run 与 PTrade 小资金实盘并行 ≥1 个月，成交/信号一致率达标后才撤本地执行腿。
4. 红线：试点期间 ADR-16 双值继续在本地腿生效；PTrade 腿仓位上限人工设定并计入总敞口语义。

### 8.1 颈线策略单文件可行性实证（2026-08-20 按码评估）

「颈线策略所有逻辑放一个 .py」按三层拆开看（行号为 master 现状）：

| 层 | 仓库真身 | 能否进单文件 | 说明 |
|---|---|---|---|
| **策略内核（识别+价位规则）** | `strategies/neckline/method_v0.py`（~650 行：`detect_neckline_method`/`_detect_core_window`/`_neckline_cluster`/`local_extrema_mask`/`compute_atr`/`_post_detect`/`DEFAULTS`）+ `signal.py`（~130 行 Signal 值对象） | ✅ **近乎逐字搬** | 纯 pandas/numpy 零仓库依赖，PTrade 内置同款库；价位规则全在 `exec_params` 键集（stop_atr_mult/tp_h_mult/tp1_h_mult/tp1_portion/max_wait/cancel_thresh_mult/max_holding/trailing 三件）——参数+算术 |
| **执行编排** | `trading/phases/pre_open.py`（~600+ 行：撤昨日单/超期平仓/ADR-16 双值/逐单挂单）+ `phases/stop_loss.py`（30s 巡检）+ `compute/stop.py` decide_cfg | ⚠️ **重写映射 ~400-600 行** | PTrade 事件模型天然同构：`before_trading_start`=撤昨日单+超期平仓+挂限价单；`run_interval`/`handle_data`=止损止盈巡检；`after_trading_end`=记录。「exec_params 定终身」语义须用 `g` 变量+研究目录 pickle 复刻（挂单时落参数快照、巡检时读） |
| **系统治理件** | job_ledger 台账/catchup 补跑/三段 gate/OrderStateMachine/fill 真相源对账/钉钉 CRITICAL 告警链/DG-G3 熔断基线兜底 | ❌ **进不去也不该进** | 这是工程可靠性面不是策略逻辑；PTrade 侧靠其自身运行保障+人工纪律补位（治理降级清单见 §六） |

**裁决：形式上成立**——单文件约 1200-1600 行（识别 ~800 逐字 + 执行 ~500 重写），PTrade 单文件体量无压力。**真正的风险不在装不装得下**：
1. **数据复权口径对拍**（最大正确性风险）：识别层吃「截至 T-1 的前复权日线」，PTrade `get_history`/内置 tushare 的复权因子时点 vs data_lake tushare qfq 口径——颈线位差一分钱、信号日期就分叉，双轨期必须逐信号对拍。
2. **巡检粒度**：30s 巡检 → `run_interval` 的粒度/时序差异影响 trailing 与 cancel_on 的触发时点（盘中 high 口径 vs 巡检时点价）。
3. **幂等语义**：DB UNIQUE + has_order 滤活态的防重挂，单文件里要用研究目录状态文件复刻（崩溃重启后不重挂/不漏挂）。

**估算**：熟练重写 2-4 天 + 双轨对照 ≥1 个月（与 §八-3 验收同窗）。

> 设计方案已出：[PTrade 颈线单文件试点设计](../superpowers/plans/2026-08-20-ptrade-neckline-pilot-design.md)（事件映射/单文件分区/状态模型/订单生命周期全集/复权对拍/双轨验收，W0 API 核对表先行）。
